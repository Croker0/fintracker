## 2. Кто чем занимается

### Штефан — главный разработчик, тимлид

**Если совсем просто.** Штефан отвечает за то, чтобы приложение работало целиком: экран открывался, кнопка сохраняла, график рисовался, а готовый файл можно было установить на телефон. Он же проверяет код остальных участников и собирает версию для сдачи.

**Что делает по шагам.**

1. Получает задачу: например, «сделать экран операций».
2. Договаривается с Кисловым, какие данные нужны экрану и в каком виде он их получит.
3. Договаривается с Давлетхановым, как экран должен выглядеть.
4. Собирает экран: кнопки, список, поиск, пустые состояния.
5. Подключает экран к данным, чтобы список и суммы обновлялись сами.
6. Проверяет поворот экрана, тёмную тему и ситуацию, когда данных нет.
7. Смотрит код других участников перед добавлением в общую ветку.
8. Собирает APK и выкладывает релиз.

**Что означают слова.**

- **Тимлид** — лидер команды разработки. Распределяет задачи и отвечает за общий результат.
- **Каркас приложения** — основа: главный экран, меню, переходы между разделами.
- **Архитектура** — общий план, из каких частей состоит приложение и как они связаны.
- **Навигация** — переходы между экранами: из «Главной» в «Операции», из списка в форму редактирования.
- **UI** — пользовательский интерфейс. Всё, что человек видит на экране: кнопки, тексты, списки, графики.
- **MVVM** — способ разделить приложение на три части: экран, логика экрана и данные. Так код проще менять и проверять.
- **ViewModel** — часть, которая хранит данные конкретного экрана. Например, выбранный период или введённую сумму. Она переживает поворот телефона.
- **StateFlow** — «поток состояния». Когда данные меняются, экран получает новое значение и перерисовывается.
- **ViewBinding** — способ обращаться к кнопкам и текстовым полям по имени, без ручного поиска.
- **Редактор операции** — форма, где вводят сумму, категорию, дату и теги.
- **Пустые состояния** — то, что показывается, когда данных ещё нет. Например, надпись «Пока нет операций».
- **График** — диаграмма: круг с долями категорий или столбики по дням.
- **Тёмная тема** — вариант оформления с тёмным фоном вместо светлого.
- **Ветка** — отдельная копия проекта, где делают изменения, чтобы не сломать основную версию.
- **Код-ревью** — проверка чужого кода перед добавлением в проект.
- **Pull request** — предложение «влить мои изменения в общую ветку». Его проверяют и только потом принимают.
- **Интеграция** — соединение готовых частей в одну рабочую версию.
- **Сборка** — превращение исходного кода в файл приложения.
- **Android** — операционная система, на которой работает приложение.
- **APK** — файл установки приложения для Android.
- **Релиз** — версия приложения, которую выложили для скачивания.

**С кем работает.** С Кисловым — по данным, с Давлетхановым — по внешнему виду, с Ибрагимовым — по сценариям и приёмке.

**Пример.** Пользователь нажимает «Добавить» → открывается форма → вводит сумму → нажимает «Сохранить» → данные уходят в базу → главный экран сам пересчитывает баланс.

**Результат.** Рабочее приложение с пятью вкладками и отдельным редактором, APK и релиз v1.0.0.

### Кислов — backend и база данных

**Если совсем просто.** Кислов отвечает за хранение данных. Когда человек добавляет трату, она не должна пропасть после закрытия приложения, а потом должна найтись в списке и графике. Кислов придумал «шкаф» с полками и правила, как туда класть и как доставать.

**Что делает по шагам.**

1. Рисует схему: какие таблицы есть и как они связаны.
2. Создаёт Entity — описание каждой таблицы кодом.
3. Пишет DAO — набор запросов: добавить, найти, удалить, посчитать.
4. Пишет Repository — посредника между экранами и базой.
5. Пишет SQL-запросы, которые считают суммы за период и по категориям.
6. Настраивает WorkManager: напоминание и фоновый бэкап.
7. Делает экспорт в CSV и JSON.
8. Настраивает CI, чтобы GitHub сам собирал проект и запускал тесты.

**Что означают слова.**

- **Backend** — часть приложения, которая работает с данными: хранит, ищет и считает. Её не видно на экране.
- **База данных** — место, где данные лежат постоянно, а не только пока открыт экран.
- **SQLite** — база, которая хранится одним файлом на телефоне.
- **Room** — библиотека над SQLite. Помогает описывать таблицы кодом и проверяет запросы при сборке.
- **Схема** — рисунок таблиц и связей между ними: что с чем соединяется.
- **Таблица** — список с колонками. Например, таблица операций.
- **Строка** — одна запись в таблице. Например, одна трата.
- **Колонка** — поле записи: сумма, дата, заметка.
- **id** — уникальный номер строки. По нему одну запись отличают от другой.
- **Kotlin** — язык, на котором написано приложение.
- **Entity** — класс на Kotlin, который описывает таблицу. Одно поле класса — одна колонка.
- **DAO** — набор функций для работы с таблицей. `insert` — добавить, `update` — изменить, `delete` — удалить, `SELECT` — найти и показать.
- **SQL** — язык запросов к базе. Например: «покажи все траты за ноябрь».
- **Агрегация** — подсчёт итогов: сумма, среднее, количество. Например, «сколько всего потрачено на продукты».
- **Repository** — посредник. Экран не лезет в базу напрямую, а просит данные у репозитория.
- **Flow** — «живой» список данных. Когда база меняется, Flow сам сообщает об этом экрану.
- **WorkManager** — системный планировщик Android. Умеет запускать задачи позже или периодически.
- **CoroutineWorker** — фоновая задача для WorkManager. Работает, даже когда экран приложения закрыт.
- **Бэкап** — резервная копия данных.
- **Экспорт** — сохранение данных из приложения в отдельный файл.
- **CSV** — файл с таблицей, который открывается в Excel.
- **JSON** — текстовый формат для хранения и передачи данных.
- **FileProvider** — безопасный способ отдать файл другому приложению: почте, мессенджеру, проводнику.
- **CI** — автоматическая проверка на GitHub: после каждого изменения проект собирается и проходят тесты.
- **Внешний ключ** — правило, которое не даёт поставить в операцию несуществующую категорию.
- **Индекс** — ускоряет поиск по колонке. Как алфавитный указатель в книге.

**Пример.** Пользователь добавляет «Продукты, 1450 ₽». В таблице `transactions` появляется строка с `categoryId = 1`. Если выбраны теги, в `transaction_tags` появляются связи с их `id`. Главная просит базу посчитать сумму за ноябрь — база возвращает готовое число, и экран рисует диаграмму.

**Результат.** Локальная `fintracker.db`, работа без интернета, напоминания, бэкап, экспорт и CI-сборка.

### Ибрагимов — аналитик

**Основные функции.** Переводит задание в требования и user stories, фиксирует must-have и could-have, пишет критерии приёмки, метрики и тест-план.

**Как работает.** Разбирает сценарии пользователя, согласует приоритеты с командой, ведёт [REQUIREMENTS.md](REQUIREMENTS.md) и [TEST_PLAN.md](TEST_PLAN.md). Проверяет сборку по чек-листу, заводит баги с шагами воспроизведения и принимает фичу после исправления.

**Результат.** Понятный объём проекта, 16 ручных сценариев и критерии, по которым фича считается готовой.

### Давлетханов — дизайнер

**Основные функции.** Отвечает за визуальный стиль: палитру, типографику, отступы, иконки, тексты и тёмную тему. Делает макеты пяти вкладок и редактора.

**Как работает.** Собирает референсы, задаёт дизайн-токены и рисует макеты в реальных пропорциях экрана. Передаёт Штефану размеры и состояния (обычное, нажатое, пустое), проверяет контраст и одинаковость отступов в готовой вёрстке.

**Результат.** [DESIGN.md](DESIGN.md), четыре макета в `docs/images/`, единый стиль светлой и тёмной темы.

## 4. Процесс работы

- **Доска:** GitHub Projects, колонки `Backlog → In progress → Review → Done`.
- **Ветки:** `main` защищена; задачи — в `feature/<краткое-имя>`, багфиксы — `fix/<...>`.
- **Коммиты:** короткие, в императиве: `feat: add period filter`, `fix: keep tag order`.
- **Pull request:** минимум 1 ревью (обычно Штефан), зелёный CI, описание изменений и скриншот UI.
- **Синхронизация:** 15 минут в начале недели + асинхронные апдейты в чате.
- **Definition of Done:**
  1. код собирается (`assembleDebug`);
  2. unit-тесты зелёные;
  3. нет новых предупреждений lint уровня error;
  4. сценарий проверен вручную;
  5. обновлена документация/строка в README при необходимости.

## 7. Риски и mitigation

| Риск | Вероятность | Влияние | Меры |
|---|---|---|---|
| Расхождение макета и реализации | средняя | среднее | макеты по реальным размерам, ревью UI |
| Сложность агрегаций по датам | средняя | высокое | SQL-группировка + unit-тесты `SummaryBuilder` |
| Нехватка времени на полировку | высокая | среднее | must-have фичи в первую очередь, could-have — в конце |
| Разные часовые пояса у команды | низкая | низкое | хранение epoch millis, локальная зона только для отображения |
| Потеря данных при смене схемы | низкая | высокое | экспорт схемы Room, версия БД, TODO на миграции |

## 8. Демо-сценарий защиты (5 минут)

1. Первый запуск: демо-данные, главный экран, переключение периодов.
2. Добавление расхода: сумма, категория, дата, тег → возврат на главную.
3. Поиск и фильтры в «Операциях», удаление операции.
4. Аналитика: топ категорий, инсайт, график.
5. Настройки: время напоминания, экспорт CSV, тёмная тема.
6. Архитектура на слайде: Room → Repository → ViewModel → UI, WorkManager, CI.
